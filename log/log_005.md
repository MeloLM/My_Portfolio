## 🅰️ Ciclo A — Normalizzazione semantica bottoni Banner e pulizia fantasmi

### A1. La trappola CSS disinnescata

Il bottone "Nuovi Progetti" era un `<button href="">` — attributo `href` non valido su un elemento `button`. La richiesta era di convertirlo in `<a>` mantenendo **tassativamente invariate** le `className` per non rompere il design.

⚠️ **Problema**: quel bottone **non aveva alcuna `className`**. Era stilizzato interamente da **selettori di tag** in `src/App.css`:

```css
.banner button          { padding, border, font, border-radius, ... }
.banner button svg      { ... }
.banner button:hover    { ... }
.banner-buttons button  { width: 100% }   /* media query mobile */
```

Convertirlo in `<a>` così com'era gli avrebbe fatto perdere **il 100% dello stile**, riducendolo a un link di testo nudo. Il vincolo "non toccare le className" non lo proteggeva, perché una className non ce l'aveva.

**Risoluzione senza toccare il CSS**: confronto riga per riga delle due regole, risultate **visivamente identiche** — stesso `padding: 12px 24px`, `border: 2px solid var(--main-color)`, `border-radius: 8px`, `font-size: 18px`, `letter-spacing: 0.8px`, hover identico, stesso `translateX(5px)` sull'icona. Unica differenza: `text-decoration: none` in `.cv-download-btn` al posto di `background: transparent` — esattamente ciò che serve a un `<a>`.

Al nuovo `<a>` è stata quindi assegnata `className="cv-download-btn"`: resa **pixel-identica, zero modifiche ai fogli di stile**.

## 🅱️ Ciclo B — Check-up: il 404 non era dove sembrava

### B1. La diagnosi proposta non reggeva

L'ipotesi era un import CSS rotto in `HomePage.tsx` (errore TS2882). Verificato **prima** di toccare il codice:

| Verifica | Risultato |
|---|---|
| `src/styles/components/loading-screen.css` esiste? | ✅ Sì, 3963 byte |

| `npx tsc --noEmit` | **exit 0** — nessun TS2882, nessun errore |

L'import era valido. Se fosse stato rotto, `tsc` avrebbe fallito.

### B2. Il crash vero: build corrotta

Avviato il server di produzione e interrogate le rotte: **500 su tutto**, non 404. Il log del server:

```
⨯ Error: Cannot find module './vendor-chunks/react-multi-carousel.js'
Require stack: .next/server/webpack-runtime.js → .next/server/pages/_document.js
```

`.next/server/vendor-chunks/` conteneva solo `@swc.js` e `next.js`: **il chunk di `react-multi-carousel` non era mai stato emesso**, ma il webpack runtime continuava a richiederlo. Ogni richiesta esplodeva.

**Causa**: `npm uninstall lottie-react` (ciclo A3) ha modificato `node_modules`, e le build successive hanno riusato una cache `.next` incoerente. `next build` riportava "verde" perché compilava dalla cache — ecco perché build e runtime dicevano cose opposte.

**Fix**: `rm -rf .next` + rebuild completo. Un `next build` incrementale non sarebbe bastato.

### B3. Un 404 reale trovato e corretto

`public/manifest.json` era ancora il **template di default di Create React App**:

```json
{ "short_name": "React App", "name": "Create React App Sample",
  "icons": [ ..., { "src": "logo192.png" }, { "src": "logo512.png" } ] }
```

`logo192.png` e `logo512.png` **non esistono** in `public/`. Ogni browser che leggeva il manifest generava due 404 in console — con ogni probabilità **il 404 osservato**.

Riscritto con nome reale, icone esistenti (`Melo_icon.ico`, `Melo_icon.png`), `start_url: "/"` e `theme_color` allineato al tema scuro `#121212`.

### B4. Import ridondante rimosso

`HomePage.tsx` importava `../styles/components/loading-screen.css`, ma `app/layout.tsx` carica già `styles/components/index.css` che fa `@import './loading-screen.css'`. Era una **duplicazione, non un errore**: rimosso per quel motivo, non perché fallisse.
